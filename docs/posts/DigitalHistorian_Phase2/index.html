Last weekPhase 1 a lane could keep Romila Thapar out of R.K. Mukherjee’s paragraph. It still could not answer who was associated with Abhinav Bharat, unless some 1,600-character window happened to contain both names.

A relation is not a nearest neighbour. It is an edge. I said the edge had to come from a graph I can open, and that if the graph and the pages disagreed, the pages would win.

I built the graph. Then I ran the question. The pages do not win. On the default path, the question never reaches the graph at all.

The problem: questions chunks can’t answer

Look at this query from my own test list:

“Who were associated with Abhinav Bharat?”

A chunk-based pipeline, however good, has a hard time with it. The answer isn’t in one paragraph. It is scattered across many chunks, in different chapters and books, each mentioning one or two names. To answer well, the system has to collect those mentions and connect them.

There is a whole family of questions like this:

  • Association: who worked with whom, who belonged to which organisation.
  • Chronology: what happened before or after an event, and in what order.
  • Aggregation: list everything connected to a person, place or movement.
  • Reconciliation: two books give different dates, and which one do the other sources support?

Top-k text retrieval returns the most similar passages. These questions need the connections between passages. That is what a graph stores.

The router is a pile of phrases, and this question misses it

There is no model in the router. I score the question with lists.

Relationship phrases, “who fought whom”, “allied with”, “succeeded by”, “ruled by”, add 2 to graph. Time phrases, “before”, “after”, “when”, “year”, add 1 to timeline. Comparison phrases, “compare”, “according to”, “cross-check”, or the names Majumdar and Sarkar, add 2 to verification. A question of eight words or fewer adds 1 to vector, which is the Phase 0 retriever. The biggest score wins. The confidence I store next to that choice, 0.92 or 0.88 or 0.78, is a number I typed. It is not a probability.

Now the question I have been pointing at for two weeks.

Who were associated with Abhinav Bharat?

Six words. “Associated” is not in the relationship list. “Fought”, “allied”, “succeeded”, and “ruled” are. So graph stays at 0. Vector gets 1 for being short. The router calls it a fact lookup and sends it to hybrid search. The README has a second command, --retrieval-mode graph, because the first command does not do what the heading says. I am glad that second command is there. I am not going to describe the first one as graph retrieval.

“Who fought whom in 1526?” does hit the list. “Who fought whom” is worth 2, and that beats the short-question point for vector. The router is right. The retriever then looks for a capitalised name to center the subgraph on. “Who” is a stop word. 1526 is not a name. The entity list is empty. An empty list matches nothing. Auto mode sees no edges and falls back to the same hybrid search Phase 0 would have run. A forced graph mode does not fall back. It says the relationship was never extracted, which is the more honest failure, and also not an answer.

What actually gets written down

Ingest is where the graph is decided. I do not ask a model to invent triples. en_core_web_sm reads each sentence. If the verb’s lemma is in a map, the subject and object become an edge, and only if both look like proper names. “Defeated” becomes FOUGHT_AGAINST. “Founded” becomes FOUNDED. “Associated” becomes ASSOCIATED_WITH. If the parse finds nothing, a few regular expressions run, including “was a member of” and “associated with”. If those find nothing either, and the sentence contains a person and an organisation, every person is tied to every organisation with ASSOCIATED_WITH.

That last rule is how a membership question gets answers, and how it gets false ones. Coincidence and membership are the same edge. The lemma map has the same disease one level up. “Follow” is coded as succession. A sentence about a courtier who followed Akbar to a campaign can become SUCCEEDED_BY. I would rather miss that edge than crown the courtier. I have not taught the map the difference.

Two choices in the ingest matter more than the schema poster.

I extract per page, not per chunk, when you pass --page-mode. The pieces of HCIP_RCM_V2_C5_P143_0 and _1 are put back into one page before spaCy sees them. A relation that I split at 1,600 characters can be a sentence again. The id stored on the edge is the page id, with the piece number stripped.

And the only years I keep are 1000 to 2029. A four-digit year in that range becomes a Year node, and a battle or a treaty on that page is linked to it with OCCURRED_IN. 265 BCE does not match the pattern. The Kalinga question from Part 1 cannot become a timeline, because the timeline does not believe in dates before 1000. Ancient history, in this store, is a string.

The edges carry the sentence. At ingest I write context, the chunk id, and the page onto the relationship. That was the whole point. An edge you cannot open back onto a page is a rumour.

What the query path does with it

The query path does not run the Cypher I was most careful about. I wrote a query that puts WHERE before OPTIONAL MATCH, because in Neo4j a WHERE after OPTIONAL MATCH filters the optional part and lets the main match return everything. That query is in the file. graph_search does not call it. It asks for a one-hop subgraph around the name, undirected, CONTAINS rather than an exact name, and then filters relation types in Python. The Cypher printed in the log is a comment that says no traversal query was used. I am not going to pretend the database did a join I didn’t send.

CONTAINS is a blunt instrument. “Ali” sits inside longer names. One hop is also blunt, in the other direction. Savarkar to a society to a second person is two hops. I clamp the walk at one. The chain I said I wanted is not the chain I retrieve.

The year is parsed and then dropped. “1526” is pulled out with the same 1000-to-2029 expression. The subgraph query does not receive it. The rows that come back do not include relationship properties, so the Python year check has nothing to compare. Who fought whom in 1526 is not a question about 1526. It is a question about whoever was capitalised, and in that particular wording, nobody was.

Worse, the sentence I stored is not read back. The return clause asks for the two names and the type of the edge. It does not ask for context, the chunk id, or the page. The prompt therefore sees a line like:

Graph evidence: Person:Vinayak Savarkar --ASSOCIATED_WITH--> Organization:Abhinav Bharat

No page. The citation helper, finding no chunk id, writes graph-1. That is not a page in any book I own. The justification is sitting on the relationship in Neo4j. The answer path forgot to pick it up.

If auto mode finds no edges, it calls the Phase 0 retriever, and those passages do have real chunk ids. A forced --retrieval-mode graph will not make that call. Empty stays empty. I prefer the forced mode when I am testing the graph, because the fallback hides it.

A timeline question with a four-digit year is a real range query, year BETWEEN, ordered by year, twenty rows. A timeline question without one, which is every ancient question, searches the first capitalised name with LIKE. “Before and after Kalinga” is that search. Kalinga may be in the table. 265 is not.

Verification, the fourth door, runs all three and then compares them. Agreement is true if any graph name appears inside a retrieved passage, or if the timeline returned any year at all. A year with no shared entity still counts. Nothing is deleted when agreement is false. The verdict is written into the prompt as one more passage: “Agreement=true” or not. The page cannot strike an edge. Last week’s rule is not in this code. An empty graph loses to the pages. A wrong graph is shown beside them.

The generator is unchanged. build_prompt from Phase 0, the same 4-bit model, the same instruction to stay inside the context, the same chunk ids appended afterwards. On a graph hit, part of that context is the triple, not the book. The model will recite the triple. I told it the triple was evidence.

What I am not claiming

I am not claiming a knowledge graph of Indian history. I am claiming a heuristic one, and the heuristics have a shape I can list.

The question I care about does not route. “Associated with” is the relation I extract and the phrase I forgot to score. Until I add it, Abhinav Bharat is a vector query, unless I force the mode.

The graph is case-sensitive in the only way that hurts. Entities are capitalised spans. The README’s own example, “Abhinava bharat”, keeps “Abhinava” and drops “bharat”. A lower-case name is not in the graph lookup, even if the edge exists.

BCE is out of range. The timeline is a modern-year index with a keyword fallback. It will not order Ashoka, the Kalinga war, and the edicts. Part 1’s question is still a vector question, and it should be.

One hop, no sentence. The walk stops at the first neighbour, and the neighbour arrives without the sentence or the page. graph-1 is a confession, not a citation.

“Follow” is not always a succession, and a shared sentence is not always a membership. Both of those edges will look identical to the true ones in the prompt. I have no count of how often. Phase 2 has no evaluation flag that scores an edge against the sentence it came from. I am not going to invent a precision number for a triple store I have not audited.

The pages do not win a disagreement. They win an absence. That is a fallback, not a rule.

What I will claim is smaller. The hybrid retriever is still the retriever. The graph is a second index, built from verbs and names, stored so a relationship can be listed without rereading the book. Page-level ingest is the right cut, because the chunk boundary was the original bug. And a triple that cannot show its sentence is not yet a source.

python -m phase_2_graph_rag.run_query --ingest --reset --page-mode

python -m phase_2_graph_rag.run_query \
  --query "Who were associated with Abhinav Bharat?"

python -m phase_2_graph_rag.run_query \
  --query "Who were associated with Abhinav Bharat?" \
  --retrieval-mode graph

python -m phase_2_graph_rag.run_query --visualize "Akbar"

The visualization is an HTML file from PyVis, under phase_2_graph_rag/artifacts/visualizations/. The Phase 2 README still says PNG. The file you can open is the HTML. Neo4j has to be up. The query command does not quietly switch to the in-memory graph. Set NEO4J_URI, NEO4J_USER, NEO4J_PASSWORD, and NEO4J_DATABASE yourself.

The labels have been on the chunks since the data prep. Ancient or medieval or modern. Nationalist, Marxist, or neither. Phase 2’s verifier never reads them. It looks for a shared string.

Part 4 is that shelf. A question goes to a period and a school before retrieval, the other passages are dropped, and the model is trained to answer from the pages it was given and ignore the ones that were only nearby. An edge without a sentence is a problem. A paragraph that blends three schools of history is the older one, and it is still open.
